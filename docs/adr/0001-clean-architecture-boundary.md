# ADR-0001. Граница чистой архитектуры проходит по артефакту модели

- **Дата:** 2026-08-10
- **Статус:** принято
- **Фаза:** 0 (решение зафиксировано заранее, применяется с Фазы 3)

## Контекст

Цель проекта — не обученная модель, а работающий ML-продукт, который не стыдно
показать. Это требует развязки слоёв: продуктовый код живёт годами, имеет
внешних потребителей и должен переживать смену модели, хранилища и фреймворка.

Одновременно ядро проекта — исследовательское. Тренировочный цикл по своей
природе процедурен, переписывается десятки раз за неделю и имеет единственного
потребителя. Любая абстракция здесь — налог: смена функции потерь начинает
требовать правки в нескольких файлах вместо одного.

Натянуть чистую архитектуру на весь проект целиком — значит замедлить
исследование. Не применять её нигде — значит получить набор ноутбуков.

## Решение

Проводим границу **по артефакту модели** (сериализованные веса + метаданные
обучения). Код до артефакта и код после артефакта подчиняются разным правилам.

Продуктовая часть строится как ports & adapters:

```
src/sillage/
├── domain/        # сущности и правила. Только стандартная библиотека.
│   └── ports.py   # протоколы: OdorPredictor, Featurizer, EmbeddingIndex
├── application/   # сценарии использования. Знают порты, не знают реализации.
├── adapters/      # реализации портов. Здесь и только здесь RDKit, torch, sklearn.
├── interfaces/    # точки входа: FastAPI, CLI.
└── research/      # ЯВНО вне чистой архитектуры: training, evaluation, experiments.
```

Инвариант: **зависимости направлены только внутрь.** `domain` не импортирует
ничего внешнего; `application` не знает, чем реализован предиктор.

Инвариант защищается автоматическим тестом в CI, а не соглашением: тест
импортирует `domain` и падает при обнаружении тяжёлых зависимостей.

## Примерная целевая структура проекта

```
src/sillage/

│   ├── note.py           # Note, Material  (мост L2)
```

## Обоснование порта `OdorPredictor`

Обычная претензия к портам — интерфейс под единственную реализацию. Здесь это
исключено конструктивно: принцип «бейзлайн раньше сложной модели» требует, чтобы
градиентный бустинг на фингерпринтах (Фаза 1) и GNN (Фаза 2) сравнивались на
идентичном сплите. Две взаимозаменяемые реализации одного контракта существуют
с самого начала — это и есть каноническое основание для порта.

## Последствия

**Положительные.** Замена модели не затрагивает API. Тесты сценариев работают на
заглушках, без RDKit и torch, и потому быстрые. Инференс на CPU не тянет за собой
тренировочные зависимости.

**Отрицательные.** Больше файлов и один лишний уровень косвенности. Требуется
дисциплина: соблазн импортировать RDKit в `application` будет возникать.

**Отложенность.** На Фазах 0–2 структура остаётся плоской. Слои разворачиваются
к Фазе 3 (первый публичный API) и окончательно к Фазе 7. Преждевременное
расслоение противоречит цели быстрых экспериментов.

## Альтернативы

- **Чистая архитектура на весь проект, включая обучение.** Отклонено: тормозит
  исследовательский цикл, который является ядром проекта.
- **Без слоёв, скрипты и ноутбуки.** Отклонено: противоречит цели «production-ready».
- **Расслоить сразу, на Фазе 0.** Отклонено: контракты, написанные до появления
  двух реальных реализаций, почти всегда оказываются неверными.
