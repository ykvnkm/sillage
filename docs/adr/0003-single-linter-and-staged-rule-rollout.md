# ADR-0003. Один линтер (ruff) и поэтапное включение правил

- **Дата:** 2026-08-11
- **Статус:** принято
- **Фаза:** 0, шаг 0.3

## Контекст

Традиционный набор Python-проекта — `black` для форматирования, `isort` для
импортов, `flake8` с плагинами для линтинга, `pylint` для глубокого анализа.
Инструменты частично пересекаются и имеют несовпадающие мнения о переносах строк,
что порождает бесконечные взаимные правки и требует конфигурации-перемирия.

Отдельный вопрос — объём правил. На пустом проекте включение всех доступных
проверок даёт сотни срабатываний, и обычный исход — линтер отключают целиком.

## Решение

**Единственный линтер и форматтер — `ruff`.** Он покрывает функциональность всех
перечисленных инструментов; `black`, `isort`, `flake8` и `pylint` в проект не
добавляются.

| Классический инструмент | Замена в ruff        |
| ----------------------- | -------------------- |
| `black`                 | `ruff format`        |
| `isort`                 | правило `I`          |
| `pyflakes`/`pycodestyle`| `F`, `E`, `W`        |
| `flake8-bugbear`        | `B`                  |
| `pyupgrade`             | `UP`                 |
| `flake8-simplify`       | `SIM`                |
| `bandit`                | `S`                  |
| `pylint` (частично)     | `PL`                 |

**Проверка типов — отдельная категория.** Линтер анализирует стиль и подозрительные
конструкции, `mypy` проверяет согласованность типов. Одно не заменяет другое,
поэтому `mypy` добавляется, но позже: без аннотаций ему нечего анализировать.

**Правила включаются поэтапно, привязанно к фазам:**

| Фаза | Что добавляем | Почему именно тогда |
| --- | --- | --- |
| 0 (сделано) | `E`, `W`, `F`, `I`, `UP`, `B`, `SIM`, `RUF` | база, работает на любом коде |
| 1 | `ANN` (обязательные аннотации) + `mypy` в мягком режиме на `src/` | появляется настоящий код, которому есть что типизировать |
| 1 | `NPY`, `PD` | приходят numpy и pandas; ловят цепочечное присваивание и подобные тихие ошибки |
| 3 | `mypy --strict` только для `domain/` и `application/` | появляются контракты (ADR-0001); в `research/` строгость остаётся мягкой |
| 3 | `S` (безопасность) | появляются FastAPI, работа с сетью и загрузка файлов |

Строгость распределяется по слоям, а не равномерно: максимальная — в ядре
продукта, минимальная — в `research/`, где код заведомо недолговечен.

## Последствия

**Положительные.** Один конфиг, один источник истины о стиле, отсутствие войн
форматтеров. Ruff на порядки быстрее, что и делает возможным его запуск в
pre-commit. Постепенное включение правил не создаёт момента, когда линтер
проще выключить, чем починить.

**Отрицательные.** Ruff реализует не все проверки `pylint`; часть глубокого
анализа остаётся недоступной. Признано приемлемым: `mypy` покрывает наиболее
ценную часть того, что даёт `pylint`.

Расписание выше — план, а не обязательство. Отклонение от него допустимо, но
должно быть отражено записью в `docs/journal/`.

## Альтернативы

- **Классический набор black + isort + flake8 + pylint.** Отклонено: медленно,
  пересекается, требует конфигурации-перемирия между инструментами.
- **Включить все правила ruff сразу.** Отклонено: сотни срабатываний на пустом
  проекте, наиболее вероятный исход — отключение линтера.
