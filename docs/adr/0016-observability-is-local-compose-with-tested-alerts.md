# ADR-0016. Наблюдаемость: Prometheus и Grafana в compose, тревоги проверяются тестами

- **Дата:** 2026-10-12
- **Статус:** принято
- **Фаза:** 2, шаг 2.9

## Контекст

Сервис отдаёт `/metrics` с шага 2.4: запросы, задержки, отказы по причинам, сходство
входа с ближайшей известной молекулой, уверенность ответов. Не хватало трёх вещей:
места, где эти метрики хранятся и видны; правила, когда на них реагировать; и
ответа на вопрос из дорожной карты — как часто реальные пользователи попадают туда,
где модель слаба.

Публичного адреса нет ([ADR-0015](0015-public-deployment-is-deferred.md)). Дорожная
карта на этот случай называла `docker-compose` для локальной демонстрации.

## Решение

1. **`deploy/observability/compose.yml`** поднимает сервис (тот же Dockerfile, что в
   CI), Prometheus и Grafana одной командой. Порты привязаны к `127.0.0.1`: у Grafana
   анонимный доступ на чтение, у Prometheus нет аутентификации.
2. **Всё — код.** Источник данных и дашборд Grafana лежат в репозитории и
   подхватываются при старте (provisioning); правка в интерфейсе запрещена
   (`allowUiUpdates: false`), чтобы дашборд не разошёлся с git.
3. **Дрейф измеряется против базовой линии.** Живое сходство входа с ближайшей
   известной молекулой само по себе ничего не говорит. Сервис при старте считает то
   же сходство для 500 молекул датасета (каждая без самой себя) и отдаёт квантили
   метрикой `sillage_baseline_nearest_similarity`. Дашборд рисует живую медиану рядом
   с этой линией.
4. **Тревоги с порогами из измерений, а не из головы:**
   - `SillageOutOfScopeShareHigh` — больше 30% запросов вне области модели 15 минут.
     Порог — из дорожной карты: при трети запросов узкий словарь элементов становится
     главной задачей (E-010). Опечатки и неизвестные названия сюда не входят: это про
     ввод, а не про покрытие модели.
   - `SillageInputDrift` — живая медиана сходства ниже 25%-го квантиля датасета 15
     минут: типичный вход стал менее знакомым, чем три четверти молекул обучения.
   - `SillageSlowPredictions`, `SillageServerErrors`, `SillageDown` — обычная гигиена.
5. **Тревоги тестируются.** `rules.test.yml` для `promtool` заставляет каждую тревогу
   сработать на синтетических рядах и промолчать там, где должна. CI-задача
   `monitoring` прогоняет эти тесты и проверяет compose и JSON дашборда.
6. **Трафик для демонстрации — синтетический** (`scripts/simulate_traffic.py`):
   фаза нормы, затем сдвиг (лекарства, галогены, соли). Скриншот дашборда в README
   подписан как синтетический.

## Чего нет и почему

- **Alertmanager** — тревоги видны в Prometheus и на дашборде, но никуда не
  отправляются. Отправлять некому, пока сервис локальный; добавить — один контейнер и
  маршрут, когда появится адрес и дежурный.
- **Дрейф разметки** — от пользователей не приходит правильных ответов. Появится,
  только если сделать «слепой тест» из CONCEPT.
- **Airflow** — по-прежнему нет; пересмотреть на Фазе 6 (ADR не меняется).

## Последствия

Мониторинг воспроизводится у любого, кто клонировал репозиторий, и показывает дрейф
на живом примере. Когда появится публичный адрес, тот же `/metrics` и те же правила
подключаются к любому Prometheus (Grafana Cloud free tier — кандидат по умолчанию),
дашборд импортируется из файла.
